# R3 USB / Wi-Fi PC 双通道切换

R3 的目标是让 USB 成为唯一活动 PC 主链路，Wi-Fi HTTP 只在 USB 未握手或已断开时承担备用通信。Wi-Fi 自身的天气和 NTP 能力不受此规则限制。

## 本轮实现

- USB 已握手时，状态或封面请求超时不再立即改走 HTTP；如果请求期间确认 USB 断开，状态和封面可以走 HTTP。
- USB 动作请求一旦发出，即使响应超时或断线也不跨通道重发；结果标记为未确认。之后产生的新动作，在 USB 未连接时可走 HTTP。
- PC 状态快照记录实际使用的传输通道；首页和诊断页显示 `USB`、`Wi-Fi HTTP` 或错误状态。
- HTTP 动作仍保留原 `request_id` 去重机制，但不再把它当作跨通道重试未知结果的理由。

## 实机验收

| 场景 | 预期 | 结果 |
| --- | --- | --- |
| USB 和 Wi-Fi 都可用 | 首页显示 PC 经 USB，诊断页显示 `PC link: USB` | 待实测 |
| USB 在线、Wi-Fi 断开 | PC 仍由 USB 提供，Wi-Fi 仅标记自身离线 | 待实测 |
| USB CDC 短暂超时但未断开 | 状态标记 USB 异常，不会同时发 HTTP；动作不重发 | 待故障注入 |
| 拔掉 OTG，Wi-Fi 仍在线 | 后续状态和新动作经 HTTP，界面显示 `Wi-Fi HTTP` | 待实测 |
| 动作发出后立刻拔掉 OTG | 该动作不跨通道重放；结果未知时 UI 显示失败/回滚 | 待实测 |
| 重新插入 OTG | 握手后恢复 USB，界面重新显示 USB | 待实测 |
| Wi-Fi 也不可用 | PC 状态标记不可用，时钟继续走时 | 待实测 |

本机构建只能验证代码可编译；上述断线、超时与屏幕显示仍需实板验收。R1 的 20 次拔插和冷启动记录也尚未完成。
