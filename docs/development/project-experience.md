## EXP-001：异步超时需要在真实 Python 版本验证

更新：2026-10-03；适用：Windows Agent 的 Python 3.10 BLE 环境与 Python 3.11 开发环境。

`concurrent.futures.Future.result()` 的超时异常在这两个环境中不能仅凭一个环境的别名关系判断。媒体动作桥同时处理 `concurrent.futures.TimeoutError` 与内置 `TimeoutError`，超时后取消尚未提交的协程；已提交的 Windows 操作不能假定撤销。

有效方法：将超时回归分别在两种真实解释器中运行。串口只读工具另用带 pyserial 的开发环境，不为了全量测试给 BLE 常驻环境添加串口依赖。入口为 `pc-agent/tests/test_windows_media_commands.py`，环境分工见[交接](../../HANDOFF.md)。

证据：前轮媒体超时兼容处理及双环境测试；本轮完整套件 137 项、BLE 相关套件 37 项通过。这个方法不证明真实播放器操作和硬件触摸已验收。

## EXP-002：系统指标按数据源隔离，并分离采样与恢复频率

更新：2026-10-03；适用：CPU/RAM、DXGI/PDH、前台项目等独立提供者。

问题：一次 GPU 查询故障会让上层丢弃整份电脑状态；启动构造失败退出采集线程后，下一次 BLE 重连也不会恢复该采集器。

有效方法：采样仍每 2 秒；初始化失败用可中断的 2–30 秒退避；失效 PDH 查询立即释放，GPU 恢复冷却 30 秒并重新枚举适配器。CPU/RAM/项目不受 GPU 故障牵连。避免用高频采样节奏反复重建资源。构造失败也要释放已获取的句柄，数组读取前验证数量与缓冲区范围，并过滤空实例名；后续 GPU 行计算忽略无效名称与非有限数值。显存用量合计超过 DXGI 总量时只将用量置为未知，避免固件严格校验拒绝包含其他有效指标的整包状态。

采集器本身若连续 3 次抛异常，应释放后回到有上限的初始化退避；单次异常保留原对象，成功采样重置计数与退避，避免永久重试损坏对象或为瞬时错误频繁重建。

格式化 GPU 数组读取须分别检查两阶段 API 状态，首次大小查询的 `PDH_MORE_DATA` 属于正常流程，返回类型使用无符号 DWORD。查询采集成功但全部数组 API 失败时也要回到现有 GPU 30 秒恢复；单类可读/成功空数组保留，避免把正常无实例和局部降级当作全部故障。2026-10-03 15:24 新增三项模拟回归先复现失败再修复，托管 108 项、两种 Python 3.10 环境定向各 11 项通过；15:41:16 已部署到常驻并恢复真实状态同步。本轮完整 150 项、实际 BLE 解释器相关 45 项通过。具体证据见[当前状态](current-status.md)。

有效验证方法补充：可在独立进程保留真实 PDH query，只给该进程的格式化调用传无效 counter 参数，触发实际 Windows API 错误；检查其他指标保留、实际句柄释放、真实冷却后重建和 GPU/显存恢复，再在 finally 关闭查询。本轮实际错误 `0xc0000bbc` 与 30 秒后恢复均有原始证据，未改变驱动或常驻查询。必须标明受控参数故障，不把它称作自然驱动/睡眠恢复；见[部署记录](deployment-20261003.md)。

证据与复现：`pc-agent/tests/test_luna_dashboard.py` 的初始化/停止/重复启动及连续采样失败后重建回归，以及 `pc-agent/tests/test_windows_dashboard.py` 的独立降级、冷却恢复、资源释放、数组边界和超额显存隔离回归。`pc-agent/tests/test_luna_dashboard_c.py` 验证固件对超额显存整包拒绝。该阶段托管套件 104 项、C 解析器 4 项通过。真实 Windows 正常只读样本及前轮部署记录见[性能记录](ui-performance-20261002.md)。2026-10-03 15:03:55 已统一部署并恢复真实状态同步，详见[部署记录](deployment-20261003.md)。模拟异常与正常运行均不能证明真实 PDH 故障、驱动重启或 Windows 睡眠/唤醒验收。

## EXP-003：构建路径采用明确优先级，设备端口要求显式指定

更新：2026-10-03；适用：Windows 上的 ESP-IDF 包装脚本、只读串口观察器和公开构建/恢复说明。

有效方法：ESP-IDF 安装路径先取脚本显式参数，再取 `IDF_PATH`；工具路径先取显式参数，再取 `IDF_TOOLS_PATH`，最后取每用户 `.espressif`。路径缺失时尽早报错；刷写、监视和有限只读观察等会接触设备的动作必须由操作者传入当前端口。这样既允许本机非标准安装，也不会把某台机器的路径或旧 COM 编号写成项目默认值。质量要求本身见[质量路线](quality-roadmap.md)，这里仅记录实现方式。

证据：`scripts/build-firmware.ps1` 的路径与端口边界检查及本机现有环境变量下的 B1 纯构建通过；构建前后镜像 SHA-256 相同。后续检查发现两个只读观察器仍有 `COM27` 默认值，现要求 `--port`，缺参在串口访问前拒绝；TF 观察器 6 项与托管套件 99 项通过。详见[当前状态](current-status.md)。新环境安装与构建、实际串口观察尚未验证，因此不能据此宣布公开构建门槛已满足。

公开文档提及仓库外恢复副本时，说明用途与保留事实即可；接手文件可用相对仓库根目录的路径定位本机副本。此次确认两份副本存在、文档检查 2 项通过，公开 Markdown 不再含本机用户目录绝对路径。路径表达修正不等于新环境构建或远端发布验收。

## EXP-004：测试入口须核对平台、依赖与实际执行边界

更新：2026-10-03；适用：Windows BLE 配套程序的 CI、完整原生回归与本地测试环境。

有效方法：把 GitHub runner 的实际 OS build 与锁定依赖的官方支持范围逐项核对；在被 Git 忽略的独立测试环境从 `requirements-test.txt` 安装依赖，并执行 `pip check` 和托管套件，不把只装运行依赖的 `.venv-ble` 当作完整测试环境。托管测试即使运行在较新 Server 镜像上，也只能证明模拟逻辑通过，真实 Windows 11 BLE 连接另行验收。

证据：将 `windows-2022` 改为 `windows-2025`；本机托管测试 98 项、预览 27 项、文档 2 项通过。随后另建 Python 3.10 `.venv-test`，从测试清单安装依赖，`pip check` 无冲突且托管测试 98 项通过；该环境已加入 `.gitignore` 并用 `git check-ignore` 验证。镜像版本、依赖支持范围及远端未执行的限制见[当前状态](current-status.md)。

完整入口也必须检查 `result.skipped`：`wasSuccessful()` 会将缺少原生前提而跳过的测试视作成功，不能仅靠日志中的 OK 判断完成。托管明确排除原生测试在执行前完成，与执行中意外跳过分开；两种模式的意外跳过均应显示原因并返回失败。2026-10-03 15:35 使用合成套件先复现完整模式误报成功，补三项回归；本机托管 111 项、完整 Python/C 150 项无跳过通过。入口为 `scripts/run-pc-agent-tests.py` 和 `pc-agent/tests/test_test_runner.py`；仍不证明远端 CI、新环境或实机验收。详见[当前状态](current-status.md)。

## EXP-005：共享单实例锁的诊断入口应在启动前说明占用者

更新：2026-10-03；适用：Windows BLE 常驻与显式前台诊断共用进程单实例锁的入口。

有效方法：在前台启动新进程前检查已安装常驻任务的运行状态，明确告知先停常驻、诊断结束后恢复；上手文档把这个顺序和期间同步暂停写在命令旁。单实例锁仍保留作最终保护，不让它的静默退出代替操作者可理解的错误。

证据：`start-ble-link.ps1 -Music -Foreground` 在本机常驻任务 Running 时按预期拒绝，PowerShell 解析和文档检查通过，未启动第二个 BLE 客户端。停常驻后的真实诊断与恢复尚未执行，不能据此声明设备连接已恢复。

## EXP-006：守护进程状态与设备链路健康分开报告

更新：2026-10-03；适用：计划任务长期运行、BLE 链路独立重试的 Windows Agent。

有效方法：状态命令保留任务 `State`，另从轮转链路日志的最新连接、健康、离线或启动事件推得 `LinkState`；超过 90 秒的事件标为 `Stale`，缺日志标为 `Unknown`。只读摘要不触发扫描、配对或进程重启，也不把旧连接事件当作当前在线。连接恢复仍需用真实设备和日志确认。

证据：本机任务为 Running，但日志到 10:00:47 连续 discovery 离线；改进后状态报告 `LinkState=Offline`。模拟日志与任务状态 5 项相关回归通过，托管套件 100 项通过。设备供电/广播和真实连接恢复未核实。

## EXP-007：隔离本地只读快照故障与 BLE 请求失败

更新：2026-10-03；适用：已认证 BLE 会话中定期生成电脑状态并发送遥测的路径。

有效方法：只捕获 `dashboard.snapshot()` 在本地生成数据时的异常，记录异常类型并按原有两秒发送节奏再试，使心跳和音乐动作继续留在同一会话。`session.request()` 的发送或应答失败可能有不确定结果，仍退出会话并遵守不重放规则；不能用同一异常处理块吞掉传输故障。

证据：`pc-agent/tests/test_luna_ble_link.py` 模拟首次快照失败后同一连接继续心跳、第二次成功发送；该阶段定向 8 项、托管套件 105 项通过，部署前未验证真实效果；当前部署状态见下文及[当前状态](current-status.md)。

部署证据补充（2026-10-03 15:07）：用户授权后重启本项目常驻，已加载包括 EXP-002 与本条在内的当前修复，自动认证并接受真实电脑状态；完整 Python/C 144 项、实际 BLE 解释器相关 42 项通过。历史“未部署”已被此记录覆盖；正常运行仍不能证明真实采集故障恢复。部署时比较当前固件构建与已烧录参考副本哈希，确认无新差异而不重复烧录；详见[部署记录](deployment-20261003.md)。无新增经验编号，沿用 EXP-002、EXP-004、EXP-006 的环境与证据方法。

## EXP-008：首次启动审计不能依赖设备已有 NVS

更新：2026-10-04；适用：天气地点、配网、绑定等持久化配置与新用户安装说明。

有效方法：审计“读缓存 → 无配置分支 → 可用配置入口 → 保存 → 重启读取”的完整链路，既查函数定义，也查所有调用者、协议动作和实际用户入口。已有设备运行成功可能依赖历史配置，不能推断空白设备可上手。通过代码检查先定位缺口，不擅自擦除真实设备的 NVS 或配对来制造空白环境。

本轮证据：全仓现行 C/H/Python/PowerShell 检索发现 `luna_weather_set_location()` 仅有声明和定义；weather worker 从 `luna_weather/snapshot` 读取地点，无有效地点则等待；当前界面显示“尚未设置地点”，现行 BLE/UI/PC 无初始化路径。根 README 与开发文档明确列为重要缺口，保持用户要求的优化暂停。未进行空白硬件配置/恢复实验；后续需专门实现并验证首次启动流程，不能把此审计当实机验收。
