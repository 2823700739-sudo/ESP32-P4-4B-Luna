# P1 稳定性修复与滑动卡片实机验证

> 本页记录三卡版本；当前四卡轮播与最新构建步骤见
> [壁纸时钟卡实机验证](p1-clock-card.md)。

## 本轮目标

本轮同时验证两项改动：

- 修复快速切歌或长时间联网后出现 `Failed to send data: 258`、
  `Unrecoverable host sdio state`，随后 P4 自动复位的问题；
- 将主页改成横向滑动卡片，并把 Codex 额度与当前项目合并显示；
- 放大音乐封面并居中显示，三个控制按钮固定在底部左、中、右位置。

音乐控制还增加了串行请求、按钮锁定和 450 ms 点击冷却。每次控制完成后，
面板都会重新读取 Windows 的真实播放状态，再决定显示 `Play` 还是 `Pause`。

## C6 固件决定

本轮保留板载 C6 固件 `0.0.6`，不单独更新 C6。

日志中的错误码 `258` 是 `ESP_ERR_INVALID_ARG`。当前组合把 Hosted Wi-Fi 的
发送缓冲区放在 PSRAM，而 P4 使用 128 字节 L2 缓存行时，1600 字节缓冲区步长
会让一半缓冲区不满足 SDIO DMA 对齐要求。本轮已在 P4 固件中把 L2 缓存行改为
64 字节，属于已知问题对应的直接规避方式。

微雪说明板载 C6 通常不需要单独烧录；需要升级时，应先确认镜像来源、版本和
恢复方法。当前官方 4B 示例仓库也没有给出可核对版本的 C6 镜像、源码和恢复
包，因此现在改写 C6 会增加不可恢复风险，不能改善本次已定位的 P4 侧问题。

参考资料：

- [Espressif esp-hosted-mcu #219：错误码 258 与 DMA 对齐原因](https://github.com/espressif/esp-hosted-mcu/issues/219)
- [微雪 4B 的 P4/C6 Hosted Wi-Fi 兼容性说明](https://github.com/waveshareteam/ESP32-P4-WIFI6-Touch-LCD-4B/blob/main/docs/p4-c6-hosted-wifi.md)
- [微雪 ESP32-P4-WIFI6 FAQ：C6 烧录注意事项](https://docs.waveshare.com/ESP32-P4-WIFI6/FAQ)

## 已实施的稳定性措施

1. P4 的 L2 缓存行从 128 字节改为 64 字节；
2. 状态轮询、封面下载和音乐命令共用一个 HTTP 互斥锁，避免同时占用 Hosted
   Wi-Fi 发送路径；
3. 音乐命令队列只保留一个待执行命令；
4. 命令提交后，上一首、播放/暂停、下一首三个按钮同时禁用；
5. Windows 返回权威状态后才重新启用按钮，并更新播放提示；
6. 状态轮询周期从 3 秒调整为 5 秒；
7. TF 卡自动挂载测试默认关闭，避免在本轮 Wi-Fi 稳定性验证中占用另一个
   SDMMC 控制器。以后单独测试 TF 卡时可在 `menuconfig` 中启用。

## 烧录步骤

先启动 Windows 助手：

```powershell
cd D:\Documents\ChatGPT\ESP32-P4-4B-Luna
.\pc-agent\start-agent.ps1
```

另开一个 PowerShell 窗口，将最新完整镜像烧录到 P4 的 `COM27`：

```powershell
cd D:\Documents\ChatGPT\ESP32-P4-4B-Luna
.\scripts\build-firmware.ps1 -Action flash-full -Port COM27
```

本轮只烧录 P4，不操作 C6。烧录完成后查看串口：

```powershell
.\scripts\build-firmware.ps1 -Action monitor -Port COM27
```

按 `Ctrl+]` 退出串口监视器。

## 第一组：启动与联网验证

1. 开机后等待面板取得 IP；
2. 确认 Windows 助手持续收到 `GET /api/v1/state`；
3. 面板顶栏的 PC 状态应由检查中变为就绪；
4. 连续观察 5 分钟。

通过标准：

- 串口没有 `Failed to send data: 258`；
- 没有 `Unrecoverable host sdio state`；
- 没有 `SW_CPU_RESET` 或反复重新显示 ROM 启动信息；
- TF 卡未插入时不再自动打印挂载失败。

## 第二组：滑动卡片验证

主页共有 `CODEX`、`MUSIC`、`WEATHER` 三张逻辑卡片。`CODEX` 卡左侧显示额度，
右侧显示当前项目名称和路径。

1. 在卡片区域向左滑，依次查看三张卡片；
2. 向右滑回第一张卡片；
3. 连续往返滑动 20 次；
4. 每次停止后检查底部序号和名称；
5. 滑到音乐卡时确认封面、中文曲名和按钮正常恢复；
6. 确认音乐封面在卡片上方居中，三个按钮位于底部左、中、右；
7. 进入诊断页再返回主页，重新检查滑动。

通过标准：

- 屏幕中央显示当前卡片，左右各露出一部分相邻卡片；
- 底部显示正确的 `n / 3` 和卡片名称；
- 同一时刻只保留三张实体卡片；
- 滑动动画结束后触摸仍有效，没有黑屏、卡死或重启；
- 音乐卡离开屏幕后再滑回来，封面和歌曲信息仍能恢复。

如果旧固件在滑到音乐卡时立即出现 `Stack protection fault`，并且回溯停在
`lv_tjpgd.c` 的 `decoder_info`，原因是约 8 KB 的 LVGL 任务栈不足以覆盖 JPEG
封面重新绑定时的解码调用峰值。当前固件已将 LVGL 任务栈提高到 16 KB，并在
卡片重建时保留同一张封面的解码缓存。

## 第三组：快速音乐控制验证

打开网易云音乐并播放歌曲，然后执行：

1. 正常速度点击下一首 5 次，每次确认曲名、封面和状态更新；
2. 快速交替点击上一首和下一首共 30 次；
3. 快速连续点击播放/暂停 10 次；
4. 停止操作，等待 10 秒，核对按钮文字和电脑上的真实播放状态；
5. 完全退出网易云，确认三个按钮保持禁用；
6. 重新打开网易云并播放，确认按钮自动恢复。

快速点击期间，已经提交命令后其余点击会被忽略，这是预期行为。通过标准是：

- PC 端不会同时收到多个重叠的控制请求；
- 面板不依据点击次数猜测播放状态；
- 最终 `Play` 或 `Pause` 与网易云真实状态一致；
- 没有 SDIO 错误、任务看门狗、栈保护错误或复位。

## 第四组：长时间稳定性验证

建议先做 30 分钟短测，通过后再做 2 小时长测：

1. Windows 助手和网易云保持运行；
2. 每 5 分钟切一次歌或播放/暂停一次；
3. 偶尔在三张卡片之间滑动；
4. 全程保留 P4 串口日志和 Windows 助手日志。

通过标准：P4 不复位，PC 状态不长期停在检查中，音乐控制可持续使用，串口不
出现 `258` 和 `Unrecoverable host sdio state`。
